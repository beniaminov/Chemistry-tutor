# План разработки RAG-системы «Репетитор по химии»

## 1. Цель и исходное состояние

Создать для редактируемого администратором сайта «Репетитор по химии» систему вопросов и ответов по школьным учебникам химии. Система должна использовать поиск по источникам (RAG), векторную базу данных, химическую онтологию и пользовательский интерфейс.

Вводные и решения, зафиксированные пользователем:

- Онтология `учебники/химия2.ttl` — OWL/RDF на русском языке, источник — `учебники/K_Zommer_Akkumulyator_Znany_Po_Khimii.pdf`.
- Единственный учебный источник для текущего корпуса RAG: `учебники/5eb6e10c5b_himija_8_klass_o_s_gabrieljan_2025_g.pdf`. Другие PDF из папки `учебники/` исключены из индекса и ответов, пока пользователь не изменит это требование.
- Язык проекта и ответов: русский.
- Для поиска использовать локальную `intfloat/multilingual-e5-base`; генерация — локальная CPU-модель Qwen2.5-1.5B-Instruct (GGUF Q4_K_M) через llama.cpp. DeepSeek API не используется.
- Требуемый режим запуска приложения — локальный.
- Исходников сайта и интерфейса в проекте нет; добавлен локальный CLI-прототип обработки PDF, поиска и генерации.

**Техническое решение:** выбран локальный Qdrant Community Edition — self-hosted использование бесплатно, лицензия [Apache 2.0](https://github.com/qdrant/qdrant/blob/master/LICENSE). Qdrant хранит векторы и JSON payload ([документация](https://qdrant.tech/documentation/manage-data/payload/)), поэтому в payload фрагментов можно помещать URI онтологических понятий и фильтровать по ним. Qdrant не является RDF/OWL-хранилищем и не выполняет reasoning; для логики и обхода графа нужен отдельный RDF-инструмент. В выбранной локальной конфигурации внешняя LLM и DeepSeek API не используются.

**Выбранная конфигурация эмбеддингов и поиска:** использовать локальную [intfloat/multilingual-e5-base](https://huggingface.co/intfloat/multilingual-e5-base), 768 измерений, префикс `passage: ` для индексируемых фрагментов и `query: ` для поисковых запросов; в Qdrant — dense-вектор с `Cosine`. Модель поддерживает русский. Ограничение входа — до 512 токенов на текст; длинные фрагменты нужно делить и не допускать молчаливого усечения. Веса модели — около 1,1 ГБ, скачиваются из Hugging Face один раз; после загрузки векторизация выполняется локально и тексты не передаются embedding API. Размерность коллекции должна совпадать с моделью; смена модели или размерности требует переиндексации.

Для первичной настройки создана [инструкция локальной E5](Локальная-E5.md), отдельные зависимости в `requirements-e5.txt` и синтетический CPU smoke/benchmark в `scripts/benchmark_e5.py`. Целевая машина: Intel Core i7-8550U, 4 физических/8 логических ядер, 8 ГБ RAM; свободно около 129 ГБ на диске C:. Повторный запуск smoke-test прошёл: кэш модели — около 1,06 ГиБ, загрузка модели — 20,4 с, peak RSS процесса — около 1,63 ГиБ, кодирование 4 синтетических фрагментов — 1,06 с, 3 запросов — 0,39 с. Это не включает Qdrant/приложение; для модели задан batch size 1. Подробности и ограничения замера — в инструкции.

Гибридный первый этап: dense-поиск локальной E5 в Qdrant + BM25 по локально загруженным текстам точек (особенно формулы, индексы/заряды и точные термины), объединение результатов через Reciprocal Rank Fusion (RRF; [документация Qdrant](https://qdrant.tech/documentation/search/hybrid-queries/)). BM25 в текущем CLI вычисляется локально в памяти, а не хранится как отдельный индекс Qdrant. Онтология — дополнительный RDF-шаг: разбор терминов и связей с помощью RDF-инструмента, затем расширение поиска/фильтрация по URI в payload; не считать BM25 или векторизацию заменой графовой логики.

Режим генерации выбран: локальная Qwen2.5-1.5B-Instruct Q4_K_M на CPU; внешний DeepSeek API не вызывается. Индексатор и CLI RAG реализованы в `scripts/local_rag.py`: OCR Tesseract обработал все 176 страниц, в локальную Qdrant-коллекцию записано 447 фрагментов с векторами 768/Cosine; BM25 работает локально по payload, результаты объединяются RRF. Полный smoke-test вопроса о правилах безопасности завершился ответом с контекстом трёх фрагментов; retrieval 12,7 с, генерация 45,5 с, наблюдавшийся peak RSS процесса 2044 МиБ. OCR-индексация заняла 1031 с. Два unit-теста лимита фрагментов прошли. Это единичная функциональная проверка, не оценка качества OCR или общего пика памяти ОС.

Выбранный учебник Габриеляна — скан: 176 страниц не имеют извлекаемого текстового слоя. Для создания корпуса добавлен локальный OCR через Tesseract (rus+eng, 180 DPI); точность распознавания формул необходимо сверять по изображению страниц. Книга Зоммера используется только как первоисточник для проверки онтологии и не включается в RAG-корпус. Онтология сверена по доступным страницам и исправлена, однако её аксиомы, свойства и экземпляры не получили сплошной постраничной атрибуции; исходный PDF является сканом.

## 2. Предлагаемая архитектура

1. **Источник знаний:** только `учебники/5eb6e10c5b_himija_8_klass_o_s_gabrieljan_2025_g.pdf`; прочие PDF и материалы не включать в RAG без нового явного решения пользователя. Сохранять сведения об издании и страницах.
2. **Подготовка корпуса:** извлечение текста, разбиение на фрагменты с контекстом заголовков, нормализация формул и обозначений, сохранение метаданных и ссылок на страницы; контроль качества извлечения.
3. **LLM-wiki по учебникам:** структурированное представление тем и понятий, связанное с исходными фрагментами и страницами. Wiki — слой навигации и редакционной проверки, а не неподтверждённая замена источникам.
4. **Онтология:** загрузка `учебники/химия2.ttl`, проверка RDF/OWL, доступ к понятиям и отношениям онтологии и связь с соответствующими фрагментами учебников. Хранить URI понятий в payload точек Qdrant; reasoning выполнять RDF/OWL-инструментом, не самой vector DB. Не изменять онтологию автоматически без проверки и истории изменений.
5. **Индекс и поиск:** гибридный поиск по фрагментам — dense-векторы + BM25 с объединением RRF, фильтры по метаданным и связям с онтологией. Повторная индексация должна быть воспроизводимой.
6. **Ответы RAG:** извлечение релевантных фрагментов, генерация ответа с понятными ссылками на источники, обработка недостатка контекста без выдумывания ответа.
7. **Сайт и административный интерфейс:** ученический интерфейс вопроса/ответа и предусмотренные роли администратора для управления материалами, индексацией, wiki и онтологией. Изменения администратора должны проходить валидацию и аудит.
8. **Harness и генерация:** использовать локальную Qwen через llama.cpp; к модели передавать не более трёх верхних фрагментов retrieval, с страницами источника. Промпты проекта вести в `Промпты-проекта.md`.

Это логические компоненты, а не предписание использовать отдельные сервисы: на этапе проектирования проверить возможность реализовать их в текущем сайте.

Подробные технические требования к harness, локальному Qdrant, индексации и обработке запроса см. в [Требованиях к harness](Требования-к-harness.md); критерии проверки поиска и локальной LLM — в [Плане тестирования RAG](План-тестирования-RAG.md).

## 3. Этапы работ

### Этап 0. Уточнение требований и границ

- Определить целевую аудиторию, классы/программу, языки, ожидаемые типы вопросов и требования к стилю объяснения.
- Проверить доступность, библиографические сведения и ограничения на обработку и показ цитат из выбранного PDF.
- Определить стек сайта и способ интеграции локального CLI/harness; локальная Qwen2.5 уже выбрана, DeepSeek API не использовать.
- Настроить локальную загрузку/кэш весов E5 и оценить CPU/RAM на контрольном компьютере.
- Сравнить локальную E5 с BM25 и объединённым dense + BM25/RRF на контрольном наборе вопросов, включая химические формулы и связи онтологии.
- Определить, какой сайт уже существует или должен быть создан, требования к редактированию контента, ролям и развёртыванию.
- Согласовать стек, модель/провайдера, требования к приватности, хранению запросов, бюджету и доступности.

**Результат:** согласованные требования, архитектурные решения и критерии приёмки.

### Этап 1. Инвентаризация и проверка данных

- Проверить структуру и корректность `учебники/химия2.ttl`, классы, свойства, аксиомы, метки, определения и источники.
- Сопоставить заявленные ссылки на страницы с доступным исходным документом; выявить пропуски и расхождения.
- Оценить качество OCR выбранного PDF, формул, таблиц и иллюстраций; остальные книги не добавлять в корпус.
- Определить формат идентификаторов источников, версий и страниц.

**Результат:** отчёт о качестве онтологии и корпуса, список проблем и правила метаданных.

### Этап 2. Прототип импорта и индексации

- Реализовать конвейер импорта только выбранного PDF с проверкой формата и понятными ошибками.
- Извлекать фрагменты, сохранять страницу, книгу/издание, главу и заголовки.
- Добавить обработку химических формул, индексов, зарядов, единиц, таблиц и типичных ошибок OCR.
- Импортировать онтологию и проверять синтаксис, URI и целостность базовых связей.
- После выбора vector DB и эмбеддингов создать идемпотентную индексацию и безопасную переиндексацию изменённого PDF.

**Результат:** повторяемый импорт, тестовый корпус, индекс и отчёт о пропусках.

### Этап 3. Поиск и ответы

- Реализовать извлечение контекста с учётом метаданных и релевантности; оценить гибридный поиск.
- Подключать только локальную Qwen; передавать максимум три наиболее релевантных фрагмента, отвечать на основе них, указывать страницы и сообщать, если доказательств недостаточно.
- Проверить вопросы на определения, уравнения реакций, расчётные задачи, сравнение понятий и неоднозначные формулировки.
- Создать эталонный набор запросов с ожидаемыми источниками и оценивать качество поиска отдельно от качества ответа.

**Результат:** прототип RAG с проверяемыми ссылками и измеримым качеством на тестовом наборе.

### Этап 4. LLM-wiki и связь с онтологией

- Определить структуру wiki: темы, понятия, связи, определения, примеры и ссылки на фрагменты/страницы.
- Генерировать черновики wiki только с источниками, затем предусмотреть проверку и публикацию администратором.
- Связать термины и отношения онтологии с понятиями wiki и материалами учебников; сохранять происхождение связи.
- Обеспечить обновление и обнаружение устаревших ссылок при изменении корпуса или онтологии.

**Результат:** прослеживаемая wiki, содержимое которой можно проверить и редактировать.

### Этап 5. Интерфейс и административные функции

- Встроить чат/форму вопросов в сайт и отображать ответ, ход объяснения при необходимости и источники с страницами.
- Реализовать управление материалами: загрузка, метаданные, статус обработки, переиндексация и журнал ошибок.
- Предусмотреть редактирование и проверку wiki, а также контролируемое редактирование/версионирование онтологии.
- Защитить административные действия авторизацией и разграничением прав; показывать статус фоновых операций.
- Проверить удобство на мобильных экранах и доступность интерфейса.

**Результат:** рабочий пользовательский и административный интерфейс, согласованный с существующим сайтом.

### Этап 6. Тестирование, эксплуатация и запуск

- Добавить модульные и интеграционные тесты для импорта, retrieval, генерации, ссылок и администрирования.
- Выполнить контрольные проверки и оценку метрик по [плану тестирования RAG](План-тестирования-RAG.md); проверить локальную генерацию и передачу не более трёх фрагментов.
- Проверить отказоустойчивость локального приложения и Qdrant, задержки и совместный расход RAM; поиск и генерация не должны вызывать внешние LLM/API.
- Провести редакционную проверку ответов по химии и тестирование некорректных/неподдерживаемых запросов.
- Подготовить инструкции по локальному запуску, обновлению корпуса, резервному копированию и откату.
- Запускать сначала на ограниченной группе пользователей, собирать обезличенную обратную связь и корректировать эталонный набор.

**Результат:** критерии качества выполнены, процедуры поддержки и обновления задокументированы.

## 4. Сквозные требования и критерии приёмки

- Каждый фактологический ответ, основанный на корпусе, по возможности сопровождается проверяемой ссылкой на книгу и страницу.
- Если надёжных источников не найдено, система явно сообщает об этом, а не маскирует отсутствие данных уверенным ответом.
- Контент wiki и связи с онтологией прослеживаются до источников; редакторские изменения версионируются.
- Повторная обработка неизменённого материала не создаёт дубликатов; изменение источника приводит к управляемому обновлению индекса.
- Формулы, индексы/заряды и ссылки на страницы проверяются отдельными тестами.
- Административные операции доступны только разрешённым ролям и имеют понятный результат/ошибку.
- До начала реализации согласуются численные пороги качества поиска, точности цитирования, времени ответа и стоимости; сейчас исходных данных для назначения этих порогов нет.
- Все изменения и проверки выполняются в рамках выбранного harness; его конкретные возможности фиксируются после выбора.

## 5. Основные риски и вопросы для решения

| Вопрос/риск | Почему важно | Решение |
|---|---|---|
| Ограничения на обработку/цитирование выбранного PDF не проверены | Может быть ограничено хранение или показ текста источника | Проверить условия использования до публикации корпуса и цитат |
| Локальная E5 работает на CPU | Индексация и поисковые запросы могут быть медленнее, а скорость зависит от RAM/CPU | Измерить скорость на целевой машине, начать с небольшого batch size; параметры модели и векторов зафиксировать |
| Ограниченные ресурсы CPU/RAM для локальной генерации | E5 и LLM могут одновременно занимать заметную память и отвечать медленно | Использовать Qwen 1.5B Q4_K_M и измерить RAM/задержку во время полного цикла; настроить CPU-параллелизм |
| Не обнаружен код сайта | Интеграционный подход и административные роли неизвестны | Предоставить репозиторий/исходники сайта и описание текущего управления контентом |
| Атрибуция онтологии к источнику частичная | Непроверенные ссылки могут давать ложную уверенность | Продолжать постраничную сверку; не считать все утверждения проверенными |
| Ошибки OCR химических формул | Искажают смысл и расчёты | Проверять извлечение и тестировать формулы на реальных страницах |
| Неподтверждённые ответы модели | Особенно опасны для учебных объяснений и решений задач | Требовать опору на найденный контекст, цитирование и явный отказ при недостатке источников |

## 6. Ближайшие действия

1. Проверить OCR и retrieval на размеченных вопросах о формулах и фактах с постраничной сверкой учебника.
2. Измерить расход RAM/задержку при работе приложения и Qdrant совместно, подтвердить качество и grounding ответов на наборе примеров.
3. Реализовать расширение retrieval по онтологии; локальная база пока не содержит проверенных связей между ontology URI и фрагментами.
4. Определить интеграцию RAG CLI с сайтом после получения исходников сайта.
