# Требования к harness и интеграциям RAG

## 1. Назначение и текущие решения

Этот документ задаёт требования к локальному процессу индексации и к оркестрации RAG для проекта «Репетитор по химии». Он не привязывает проект к конкретному языковому фреймворку: код приложения пока отсутствует, поэтому выбор harness-библиотеки нужно сделать после выбора стека сайта. Любой выбранный harness обязан реализовать и проверять требования ниже.

Зафиксированные компоненты:

- Локальная Qdrant Community Edition в persistent embedded режиме — хранение dense-векторов и payload; BM25 вычисляется локально по текстам в payload, затем dense и lexical результаты объединяются через RRF.
- Локальная `intfloat/multilingual-e5-base` — embeddings размерности 768; `passage: ` для документов, `query: ` для вопросов, `Cosine` в Qdrant. Ограничение — 512 токенов на вход; веса около 1,1 ГБ.
- Гибридный поиск dense + BM25 с объединением через RRF.
- Локальная Qwen2.5-1.5B-Instruct GGUF Q4_K_M через llama-cpp-python — генерация на CPU без внешнего API.
- Химическая онтология `учебники/химия2.ttl` обрабатывается отдельным RDF-инструментом; Qdrant не выполняет OWL/RDF reasoning.
- Единственный разрешённый документ в RAG-корпусе: `учебники/5eb6e10c5b_himija_8_klass_o_s_gabrieljan_2025_g.pdf`. Книга Зоммера — только источник онтологии, не источник RAG.

Индексация, retrieval и генерация выполняются локально. DeepSeek и другие внешние LLM/API не используются.

## 2. Требования к harness

### 2.1 Компоненты и поток запроса

Harness должен разделять и явно связывать этапы:

1. Проверка и нормализация запроса, язык ответа — русский.
2. Поиск по понятиям и связям RDF-онтологии.
3. Получение query embedding локальной E5, dense-поиск в Qdrant и BM25-поиск по тексту; объединение результатов RRF.
4. При необходимости — уточнение кандидатов фильтрами и URI онтологии в payload.
5. Сборка контекста с точными страницами/метаданными источника.
6. Генерация ответа локальной Qwen с инструкцией отвечать только на основании предоставленных материалов; в prompt включать не более трёх верхних результатов RRF.
7. Проверка формата ответа и ссылок, затем возврат ответа пользователю.

Каждый этап должен иметь типизированный вход/выход, измеряемые метрики и явно обрабатываемую ошибку. Ошибка локальной модели, пустая выдача, неверный ответ или отсутствие доказательств не должны маскироваться успешным ответом.

### 2.2 Построение и обновление базы

- Разрешать индексацию только для явно настроенного пути выбранного PDF; не сканировать каталог учебников автоматически.
- Перед извлечением проверить, что файл существует, соответствует allowlist и его SHA-256 записан в манифесте индекса.
- Сохранять на каждой точке как минимум: идентификатор документа/издания, номер страницы (или диапазон), стабильный ID фрагмента, текст фрагмента, хеш текста, URI связанных понятий онтологии, версию/имя модели embeddings, размерность и версию схемы индекса.
- Разбиение на фрагменты должно сохранять границы страниц и заголовки; не объединять текст так, чтобы потерялась проверяемая ссылка на страницу. Правила сегментации и нормализации формул хранить в конфигурации с версией.
- Индексация должна быть идемпотентной: повторный запуск с тем же PDF и конфигурацией не создаёт дубликатов. Изменение PDF, модели, размерности или алгоритма разбиения порождает новую версию индекса и требует полного пересчёта соответствующих векторов.
- Обновление выполнять безопасно: сначала собрать и проверить новую версию коллекции, затем переключить приложение на неё. При неудаче сохранить рабочую версию и явно сообщить об ошибке.
- Проверять размерность каждого embedding и соответствие `Cosine`/схеме коллекции до записи. Сохранять счётчики страниц, чанков, пропусков и ошибок.
- После импорта делать контрольную выборку фрагментов с исходными страницами и проверять формулы/OCR вручную или тестом; некорректные фрагменты не должны молча попадать в продукционный индекс.
- Онтологические URI должны быть валидированы по загруженному RDF-графу. Отсутствие сопоставления допустимо и должно представляться пустым списком, а не выдуманной сущностью.

### 2.3 Локальная Qdrant

- Qdrant запускать как локальный сервис, доступный только с loopback/внутреннего интерфейса; не публиковать его HTTP/gRPC-порты в Интернет или публичную сеть.
- Закрыть административный доступ и не включать Dashboard/API без ограничений на недоверенном интерфейсе. При использовании Docker закрепить образ/версию, хранить данные в постоянном локальном томе и не публиковать порты без явной необходимости.
- Проверить доступность, версию сервера, ожидаемую коллекцию, размерность и наличие схемы payload перед каждым индексированием и поиском.
- Определить резервное копирование локального хранилища и проверить восстановление на отдельной тестовой копии. Не считать сам факт наличия каталога данных проверенной резервной копией.
- Хранить конфигурацию, URL сервиса, коллекцию и пути к файлам отдельно от секретов; реальные ключи — только в локальном хранилище секретов/переменных окружения.

### 2.4 Локальная модель и сетевые границы

- E5 и GGUF-модель загружаются отдельно, закрепляются по revision/версии и после установки запускаются с локальных файлов; runtime не должен скачивать модель автоматически.
- Retrieval/генерация не должны обращаться к внешним провайдерам или API. Проверять локальный режим по отсутствию сетевых вызовов во время вопроса.
- В логах допустимы модель, задержка, ID найденных фрагментов и причина отказа. Не логировать полный текст учебника, полный prompt/context по умолчанию.
- Учитывать, что prompt содержит вопрос и до трёх отобранных фрагментов; ограничивать размер каждого фрагмента и суммарный размер context.

### 2.5 Контракт промпта и ответа LLM

- В запрос включать исходный вопрос, релевантные найденные фрагменты с номерами страниц и только необходимые метаданные.
- Явно инструктировать модель: отвечать на русском, опираться на переданные материалы, отличать сведения учебника от пояснений, не придумывать факты/цитаты/страницы, сообщать о недостатке контекста.
- Рассматривать текст вопроса, PDF и поисковых фрагментов как недоверенные данные, а не как инструкции для harness. Игнорировать команды, найденные внутри источника, которые пытаются изменить системные правила, раскрыть секреты или инициировать действия.
- Жёстко ограничить число включаемых фрагментов тремя (независимо от ranking); также ограничить общий размер контекста и выходных токенов; не передавать весь PDF.
- Ответ должен содержать проверяемые цитаты/ссылки на страницы только из фактически переданного контекста. Если подтверждённого ответа нет, вернуть предусмотренный отказ/уточнение, а не заполнить пробел догадкой.
- По возможности получать ответ в структурированном формате (ответ, список источников `{document_id, pages, chunk_id}`, статус достаточности контекста) и валидировать его до показа. Если формат невалиден, выдавать явную ошибку или ограниченный повтор с исправляющей инструкцией, не создавать фиктивные ссылки.

## 3. Требования к настройке

Конфигурация должна задаваться вне кода и версионироваться без секретов. Минимальный набор параметров:

| Параметр | Требование |
|---|---|
| Путь к исходному PDF | Точный allowlisted файл, без автоматического glob |
| Qdrant storage path и имя коллекции | Persistent локальный каталог, проверка доступности и схемы |
| Embedding model/dimension/metric | `intfloat/multilingual-e5-base` / 768 / `Cosine` |
| E5 prefixes/limit | `passage: ` для чанков, `query: ` для вопроса; максимум 512 токенов на текст |
| Chunking | Размер, overlap, правила границ страницы и нормализации формул; конфиг версионируется и уточняется после оценки извлечённого PDF |
| Hybrid search | Отдельные лимиты dense и локального BM25, правило объединения `RRF`, итоговый top-3 для контекста |
| RDF | Путь к TTL, проверка парсинга и политика раскрытия связей/URI |
| LLM | Локальная Qwen2.5-1.5B-Instruct GGUF Q4_K_M через llama.cpp; нет внешней генерации |
| Ограничения | Максимум 3 фрагмента, лимиты контекста/выходных токенов, CPU threads, обработка ошибок локальной модели |
| Логи | Уровень и режим редактирования содержимого; безопасная конфигурация по умолчанию |

Не фиксировать без измерений: размер фрагмента, overlap, top-k, порог релевантности, лимиты стоимости и допустимую задержку. Сначала получить baseline на тестовом наборе, затем утвердить численные критерии.

## 4. Условия готовности к реализации

- Выбран стек сайта и harness-библиотека; обосновано, что она позволяет контролировать шаги, типы данных, ошибки и передачу контекста.
- Определены точные версии API/моделей и конфигурация dev/test/prod без секретов в репозитории.
- Реализованы unit-тесты локального контракта генерации и ограничения не более трёх чанков.
- Проверено, что retrieval и генерация не выполняют внешних сетевых запросов.
- Тестовая база и тестовые вопросы отделены от продукционной коллекции.
- Все критерии из [плана тестирования RAG](План-тестирования-RAG.md) выполняются либо явно зарегистрированы как известные ограничения.
